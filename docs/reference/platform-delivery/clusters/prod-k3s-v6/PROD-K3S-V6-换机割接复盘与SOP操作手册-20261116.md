## 3. 标准化 Step-by-Step SOP 操作手册

任何工程师按照以下 8 个阶段步骤，均可 100% 幂等复现迁移过程。

### 阶段一：目标节点基础初始化与 GitOps 部署 (P1 - P4)

1. **主机前置依赖与 OS 身份初始化（对应 `vhosts/common`、`vhosts/k3s-cluster-server`）**：
   - **操作系统与内核模块**：目标节点使用 Debian 12+（本轮为 Debian 12 Bookworm；若为 RHEL 系需确保同内核版本的 `kernel-modules`、`iptables-nft`、`nftables`、`conntrack-tools` 已安装）。确保启用 `wireguard`、`br_netfilter`、`overlay` 内核模块（可持久化至 `/etc/modules-load.d/k3s.conf`）。
   - **网络转发参数**：
     ```bash
     cat <<'EOF' | tee /etc/sysctl.d/90-k3s.conf
     net.bridge.bridge-nf-call-iptables = 1
     net.bridge.bridge-nf-call-ip6tables = 1
     net.ipv4.ip_forward = 1
     EOF
     sysctl --system
     ```
   - **系统基础软件包**（`k3s_platform_bootstrap_packages`）：Debian 系安装 `curl`、`git`、`openssh-client`、`ca-certificates`、`python3-pip`、`tar`，以及跨云隧道所需的 `wireguard-tools`：
     ```bash
     apt-get update && apt-get install -y \
       curl git openssh-client ca-certificates python3-pip tar wireguard-tools
     ```
   - **主机名固化与本地解析**（`vhosts/common/tasks/node_bootstrap.yml`）：防止重启后 cloud-init 覆盖节点名（保留逻辑名 `prod-k3s-v6`）：
     ```bash
     mkdir -p /etc/cloud/cloud.cfg.d
     echo "preserve_hostname: true" > /etc/cloud/cloud.cfg.d/99-k3s-platform-hostname.cfg
     hostnamectl set-hostname prod-k3s-v6
     # 确保 /etc/hosts 包含: 127.0.1.1 prod-k3s-v6
     ```
   - **三权分立 OS 身份（`vhosts/common/tasks/os_identity.yml`）**：从 Vault 路径 `kv/prod/security/{root,operator,auditor}` 提取 `authorized_keys`，在目标机建立 `root`、`operator`、`auditor` 账户与隔离权限。

2. **`ansible-pull` 依赖与自收敛定时任务初始化（对应 `vhosts/ansible_pull_timer`）**：
   - **前置依赖**：目标主机需具备 `git` 与 `ansible-core`（提供 `ansible-pull` 可执行文件），并准备持久化检出目录 `/var/lib/ansible-pull/playbooks`（`0750`，属主 `root:root`）。
   - **自动化下发**（由 `k3s_platform_bootstrap.yml` 在 `ansible_pull_timer_enabled: true` 时自动执行，也可通过 `ansible-pull-timer.yml` 独立下发）：

     ```bash

       -U https://github.com/ai-workspace-infra/playbooks.git \
     ```

### 阶段三：Vault 状态与凭证迁移 (P6.1)

Vault 承担动态凭证、数据库密码及 PKI 证书签发，同版本严禁拷贝物理目录，必须采用 Raft Snapshot。

1. **源端导出 Raft 快照**：
   ```bash
   export VAULT_ADDR=https://127.0.0.1:8200
   export VAULT_TOKEN="<OPERATOR_TOKEN>"
   vault operator raft snapshot save /tmp/vault_prod_source.snap
   sha256sum /tmp/vault_prod_source.snap
   ```
2. **通过隧道传输至目标端容器**：
   ```bash
   scp /tmp/vault_prod_source.snap root@10.254.253.2:/tmp/
   # 在目标机拷贝进 Pod
   kubectl cp /tmp/vault_prod_source.snap vault-prod/vault-0:/vault/data/vault.snap
   ```
3. **强制恢复快照并解封**：
   ```bash
   kubectl exec -n vault-prod vault-0 -- vault operator raft snapshot restore -force /vault/data/vault.snap
   # 输入源集群原始 Shamir Key 解密
   kubectl exec -n vault-prod vault-0 -- vault operator unseal <SHAMIR_UNSEAL_SHARE>
   ```
4. **重写目标集群 Kubernetes Auth 与 ESO 对账**：
   ```bash
   # 更新 auth/kubernetes 配置指向目标本地 K3s API
   kubectl exec -n vault-prod vault-0 -- vault write auth/kubernetes/config \
       kubernetes_host="https://kubernetes.default.svc:443"
   
   # 校验 17 个 ExternalSecret 全部同步
   kubectl get externalsecrets -A
   # 预期：所有项均为 SecretSynced: True
   ```

### 阶段四：PostgreSQL 基础全量逻辑迁移 (P6.2)

1. **导出全局角色与业务数据库**：
   ```bash
   # 源端执行
   k3s kubectl --kubeconfig=/etc/rancher/k3s/k3s.yaml exec -n postgresql-prod postgresql-postgresql-0 -- \
       sh -c 'PGPASSWORD=$POSTGRES_PASSWORD pg_dumpall -g' > /tmp/pg_globals.sql
   k3s kubectl --kubeconfig=/etc/rancher/k3s/k3s.yaml exec -n postgresql-prod postgresql-postgresql-0 -- \
       sh -c 'PGPASSWORD=$POSTGRES_PASSWORD pg_dump -Fc -Z 6 -d account' > /tmp/account.dump
   
   scp /tmp/pg_globals.sql /tmp/account.dump root@10.254.253.2:/tmp/
   ```
2. **目标端导入全局角色与业务结构**：
   ```bash
   # 目标端执行
   kubectl exec -i -n postgresql-prod postgresql-postgresql-0 -- \
       sh -c 'PGPASSWORD=$POSTGRES_PASSWORD psql -U postgres' < /tmp/pg_globals.sql
   
   kubectl exec -i -n postgresql-prod postgresql-postgresql-0 -- \
       sh -c 'PGPASSWORD=$POSTGRES_PASSWORD pg_restore --clean --if-exists --no-owner -d account' < /tmp/account.dump
   ```
3. **基础 73 张表结构与行数核验**：
   ```bash
   kubectl exec -n postgresql-prod postgresql-postgresql-0 -- \
       env PGPASSWORD=$POSTGRES_PASSWORD psql -U postgres -d account -t -A -c \
       "SELECT count(*) FROM information_schema.tables WHERE table_schema='public';"
   # 预期返回：73
   ```

## 4. 关键踩坑点与避坑指南 (Lessons Learned)

1. **PostgreSQL 逻辑恢复唯一索引冲突**：
   - *问题*：直接 `pg_restore` 会因为既有临时表或者序列已存在而产生冲突（例如 `idx_email_deliveries_dedupe_key` 报错）。
   - *解法*：在最终增量恢复前，先在事务中执行 `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` 清空表空间后再恢复，保证 100% 洁净幂等。
2. **Traefik `ServersTransport` 缺失问题**：
   - *问题*：新节点部署 Traefik 后，访问 `vault.svc.plus` 返回 HTTP 404，原因是 IngressRoute 指定了 `serversTransport: vault-transport` 但对应命名空间未声明该 CRD 实例。
   - *解法*：在 `vault-prod` 命名空间下显式补齐 `ServersTransport` 资源配置并入库 GitOps。
3. **Cloudflare 凭据属性隔离**：
   - *问题*：以 `cfat_` 开头的 Token 是 Zero Trust Access 凭证，直接请求 Client API 会报 HTTP 403 / 401。
   - *解法*：区分好 Zero Trust Service Token 与 Zone DNS API Token（需要 `Zone:DNS:Edit` 权限）。
4. **WireGuard / 内网 MTU**：
   - 跨云隧道 MTU 推荐设置为 1420，保证大数据块传输稳定不发生丢包或分片挂死。
