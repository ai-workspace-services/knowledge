# XConnect 日本 HAProxy 试点规划草稿

状态：待实施。目标是在日本区用独立入口调度多个 Xray 后端，先验证节点故障切换，再验证入口故障切换。优先复用已有的独立宿主机、Caddy/Xray 和 Agent。

## 域名与路由

| 新入口 | 后端池 | 开放顺序 |
| --- | --- | --- |
| `jp-xconnect-plus.svc.plus` | JP Plus A / B | 首批，仅测试账号 |
| `jp-xconnect-free.svc.plus` | JP Free A / B | Plus 验收后 |
| `jp-xconnect-pro.svc.plus` | JP Pro A / B | Plus 验收后 |
| `jp-xconnect-custom-<id>.svc.plus` | 对应专属池 | 专属权限验收后，按具体 ID 配置 |

入口运行官方 HAProxy 3.4 LTS，试点基线为 3.4.7。部署记录应固定制品版本及校验值。组织 [HAProxy fork](https://github.com/ai-workspace-xstream/haproxy) 跟踪上游，试点使用 [官方发布制品](https://www.haproxy.org/download/3.4/src/)。

HAProxy 在 TCP 443 上按 TLS SNI 转发，未知域名拒绝连接。后端保留 TLS 终止，由 A、B 分别提供覆盖对应新域名的证书。对于共享一个 SNI 和端口的两种传输，须先验证后端能正确分流，或使用独立入口端口。XHTTP 验收覆盖同一会话的上下行请求，确认所用客户端模式在跨 TCP 连接调度时正常，必要时为同一会话设计后端亲和策略。

## 上报、授权与可用性

- **Agent** 保持独立节点 ID，沿用 Accounts 授权同步。池成员必须同步一致的有效 UUID 名单及套餐、白名单和团队范围。Xray 在后端校验 UUID。
- **HAProxy** 按配置中的 SNI 和池成员转发。首阶段用 TCP 检查验证连通性。联动阶段改为探测 Agent 私网 `/readyz`，并验证代理入站可达。Agent 用同一就绪判定生成探测结果和 Accounts 心跳，纳入维护状态、入站状态、授权快照是否成功应用及同步有效期。
- **Accounts** 保留现有 Agent `entryPoint`。新入口通过独立试点映射绑定现有池成员，先仅向授权测试账号下发。入口采集器从本地 HAProxy 状态接口读取可接收新连接的后端，并通过认证上报入口、池、Agent ID 和采集时间。对试点池，Accounts 只在存在一台同时满足 Agent 就绪、授权范围匹配和入口可调度的后端时标记可用。缺失或过期的入口状态视为不可用。采集器使用只读权限，私网探测不暴露用户凭据。
- **统计** 保留各后端的原节点身份用于流量归集。统一域名用于连接和节点池展示。

## 渐进实施与验收

1. **东京 Plus 试点。** 确认两台可复用且位于不同宿主机的 Plus 后端、独立 HAProxy 入口 IP、后端端口及证书续期归属。先直测新域名的 TLS 和业务握手，再开通测试 DNS。先使用指定 SNI 的客户端配置验证转发，不改现有订阅。
2. **接通状态联动。** 测试有效与未授权 UUID 在 A、B 的结果一致。摘除 A 后，池保持可用且客户端重连走 B。A、B 均不可调度时，Accounts 将新入口标为不可用。恢复 A 时，在授权同步成功后才恢复调度。覆盖入口到后端网络断开、Agent 心跳过期和入口采集过期。
3. **完成入口冗余后扩池。** 单台 HAProxy 试点验证的是后端容错。正式推广前，将两台 HAProxy 放到不同故障域，接入带健康检查的四层入口，验证失去任一 HAProxy 时能重连。通过后开放 Free、Pro 和专属池，并验证不同池之间的授权隔离。

回退时关闭新入口的试点下发，保留原入口供客户端使用。DNS、证书及运行变更单独记录。当前已创建 fork，本草稿未开通 DNS 或部署入口。
