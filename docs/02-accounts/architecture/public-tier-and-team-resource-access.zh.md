# Shared、Plus、Pro 与 Team 资源访问白皮书

设计日期：2026-10-21。规则已经用户确认；本文作为实现与权限矩阵测试的依据，**不声明代码已合并或已上线**。部署与当前验收状态另记。

## 1. 资源模型

个人资源按权益递增：`Free ⊆ Plus ⊆ Pro`；按降级方向逐级缩小。`shared/free` 是基础资源，`plus` 是新增付费资源。Pro 的当前资源视图是二者合集，不为每个 Pro 用户创建新主机、复制节点或发放专属资源。

`Team` 是唯一按具体团队归属的专属资源，完全独立于个人等级继承。购买 Pro 不会取得 Team 资源。Team alpha 的身份或管理员身份不会取得 Team beta 的可见性。

| 用户身份／场景 | shared/free | plus | Pro 聚合视图 | 所属 Team | 其他 Team |
| --- | --- | --- | --- | --- | --- |
| Free 个人用户 | 可用 | 不可用 | 不可用 | 不可见 | 不可见 |
| Plus 个人用户 | 可用 | 可用 | 无单独入口要求 | 不可见 | 不可见 |
| Pro 月付／年付个人用户 | 可用 | 可用 | shared/free ∪ plus | 不可见 | 不可见 |
| Team 专属成员 | 沿用 dedicated-only 隔离 | 同左 | 同左 | 可见且按团队权益使用 | 不可见 |
| 普通 admin／operator | 按本人套餐 | 按本人套餐 | 按本人套餐 | 仅本人有效所属团队 | 不可见 |
| root 管理视图 | 全量可见 | 全量可见 | 全量可见 | 全量可见 | 全量可见 |

root 的库存检查权与用户代理使用权分离。root 可以检查关闭、过期和跨团队资源；不能因此自动获得客户代理 UUID 或绕过暂停、账务、有效期及连接授权。

普通 admin/operator 可保留关闭节点的诊断信息，但必须先按本人的套餐/所属团队过滤；诊断能力不能扩大资源范围或泄露其他团队。

节点若上报已有 `resource:pro`，仍只允许 Pro 个人权益；这不是当前 Pro 聚合视图成立的前提，也不要求部署这种节点。无独立 pro 节点时，Pro 仍能使用全部符合条件的 shared/free/plus 节点。

## 2. 权威依据与控制点

Accounts 是授权事实来源：个人当前权益由受审核的套餐、计费 profile 和有效用户分组计算；Team 依据有效 membership、团队状态/有效期与 enrollment 归属。前端按钮、节点名字含 plus/pro、DNS 后缀、用户可编辑标签均不授予权限。

实现采用同一公共资源继承判断，供以下入口复用：

1. 用户节点发现及连接配置：返回可用且属于允许范围的节点。
2. Agent 全量用户配置：Free 节点收到符合基础权益的 Free/Plus/Pro；Plus 节点收到 Plus/Pro；Pro 节点收到 Pro；Team 节点仅收到所属团队的有效用户。
3. Agent 增量配置与重连：与全量配置同一授权条件，升级、降级、暂停和团队变更不会残留越权 UUID。
4. 区域入口库存：root 全量；其他调用者按自身个人权益或有效 Team 范围过滤。通用 admin/operator 角色不能绕过 Team 隔离。

禁止仅修前端显示、仅修节点发现，或让 Agent 继续使用旧的精确等级匹配。否则可能出现“看得到但连不上”或“看不到但仍下发用户”的不一致。

有效性门禁保持在继承判断之外：账号 active、未封禁、未暂停、配额可用、代理凭据有效、团队未过期，且节点健康、新鲜、开放。未知/矛盾的资源类别或团队归属拒绝访问。

## 3. 页面呈现

布局保持不变。普通用户节点选择器显示其实际可用节点；Pro 是聚合视图，不凭空显示一个没有可用地址的“专属 Pro 节点”。当前 Free 用户只看到基础池属于正确授权行为；付费用户不能因缺少物理 pro 池失去基础及 plus 资源。

Team 节点的域名、teamId、pool 数和关闭原因都属于团队范围元数据。非所属团队及非 root 的接口响应中不返回这些字段，再交由前端呈现；不能只在 UI 隐藏。

额度用尽时显示“额度已用尽 · 已暂停”，并说明可以通过升级套餐恢复。恢复条件是付款经核验、新权益生效且新额度允许访问；同周期升级保留已用量、不叠加额度、不重置用量。配额续期或经审核调整后也可恢复。说明不得承诺点击付款按钮就立即恢复。

## 4. 权限矩阵测试

| 测试层 | 必须覆盖的正例 | 必须覆盖的反例 |
| --- | --- | --- |
| 公共继承 | Free→基础；Plus→基础+Plus；Pro→基础+Plus+已有Pro | Free不能Plus/Pro，Plus不能Pro，未知class拒绝 |
| Pro 聚合 | 仅 shared/free/plus 节点时 Pro 仍取得完整合集，去重 | 不要求伪造物理 pro 池，不包含 Team |
| 团队范围 | root可查看全部；alpha成员仅alpha；beta成员仅beta | 普通admin/operator/个人Pro不能查看跨Team；移出/过期/停用后不可见 |
| 用户节点 API | 节点集合与权益矩阵一致，过滤关闭/过期状态报告 | 401匿名、暂停/配额/过期限制保持；无跨团队节点元数据 |
| Agent 全量下发 | Free/Plus Agent包含新增允许的Pro用户 | 各节点不接收高于权益或跨Team用户，暂停/黑名单用户排除 |
| Agent 增量/重连 | 与全量结果一致；升级可新增，降级/移出可移除 | 缓存或旧事件不能恢复已撤销权限 |
| 前端 | 标签和分组支持Pro，保持实际端点/SNI/端口/传输路径 | 空数据/非法payload不伪造节点，未知类型不静默提升权限 |

测试应包含用户套餐 × 节点class × 团队归属 × 管理角色的组合；使用隔离 fixture，不修改真实订阅来制造测试样本。将根本不支持的类别/冲突组也加入反例，验证 fail-closed。

## 5. 配置、数据和交付边界

此设计不引入新 SQL schema，不创建用户级数据库角色，不复制资源或重写订阅/配额/账本。个人等级继承属于 Accounts 授权逻辑；实例、DNS 和部署代际只属于基础设施声明。

实现顺序：Knowledge 设计 PR → Accounts 同一授权函数及矩阵测试 → Portal 展示/类型/状态提示 → 审查合并 → 固定构件和 GitOps 声明 → SSH/Playbook/Doco-CD 部署 → 真实节点发现、配置下发和连接验收。测试成功、合并和线上生效分别报告。

当前发现的 Pro 问题是精确等级匹配阻止其继承 Plus/Free；Plus 用户分组存在时仍应单独验证实际请求、配额状态和节点新鲜度，不能将两类现象都归因于同一问题。
