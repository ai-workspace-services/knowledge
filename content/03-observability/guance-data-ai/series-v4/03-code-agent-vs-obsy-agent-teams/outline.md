# 03｜同一场线上排障：Coding Agent 和观测 Agent 谁更适合独立开发者？

**公众号备选标题**：同一个线上问题，让 ChatGPT、Claude Code 和观测 Agent 分别查一遍

**小红书封面**：AI 都会排障，为什么还要观测 Agent？

## 选题与边界

一个人维护个人 SaaS，收到告警后，可以让通用 AI/编码工具查看代码、日志和 Grafana，也可以让 Obsy Agent Teams 按授权检查观测数据。本文要比较的是**相同问题下的信息获取、证据与人工成本**，不预设哪一方更准。ChatGPT 是产品入口，具备终端/工具能力的具体模式及 Codex、Claude Code、Antigravity 的版本和接入方式要单独记录，不把它们等同为同一种产品或模型。未参与实测的工具不纳入排名。

区分两类场景：**日常巡检**检查同一时间窗口是否存在异常；**故障排查**围绕已知异常定位可能原因。若只有一个案例，优先完成故障排查，巡检作为后续扩展；不要把单次排查外推成长期自动巡检成效。

已有 [OPE 开篇案例](../../articles/00-nov-opener-ope-case/article_draft.md)提供两次流水线故障的历史素材；其中 Obsy 一侧尚待实测。第 3 篇以该案例为起点，避免把厂商文档或设想写成实测结果。

## 最小可复验 case

- 优先选一条 **UAT 的受控慢请求或既有、已授权的历史事件**：入口 Worker → Cloud Run 服务 → 数据库依赖，预先固定时间窗、版本及已知事实；依赖端没有遥测时标注盲区。已有生产事故也可用脱敏证据离线复盘，只读观察；不为文章制造生产故障。
- 至少两组：A 通用 Agent 通过实际可用的只读工具查询 Grafana/OTel 和代码；B Obsy Agent Teams 使用实际获得授权的工作空间信号。若各工具尚未开通，记录未测试而非以假设补全。生产账户和数据库账户强制只读，不执行变更、重启、修复或发通知。
- 两组提供同一故障描述、时间窗口和同等可观察信息；冻结数据快照与查询范围，记录工具链、模型、版本、提示词和上下文。先分别独立回答，再可追加互补信息做第二轮；避免不同权限、数据或已知答案造成不公平。若本身要比较原生接入，另设“各自默认配置”探索组，不与公平组混成胜负结论。
- 事先建立人工核对的事实清单，保留未知项；以原始日志、指标、Trace、部署版本交叉印证，不以任一 Agent 输出作为标准答案。

## 观察与记录

| 对比项 | 客观记录 | 解释边界 |
| --- | --- | --- |
| 进入问题的准备 | 凭据授权、工具接入、部署和配置时间 | 也记录 Obsy Agent 的运行环境成本及权限配置 |
| 可访问的数据 | 代码、版本、Grafana/OTel 与观测云信号范围 | 没接入的信号记为不可见；不同数据源覆盖分别说明 |
| 分析过程 | 查询、证据链接、假设及验证路径、无法回答之处 | 表达流畅不等于诊断正确；区分相关性与根因 |
| 人工与时间 | 首条证据、可复核结论的耗时、人工干预次数 | 记录起止标准与数据等待时间，不做无基准宣称 |
| 成本与风险 | 订阅或 API 费用口径、Obsy 积分、运行资源及敏感数据外发 | 订阅与 API 单价不随意换算；无法取得就标未知 |
| 结论与组合 | 被人工验证的发现、误判与盲区 | 只比较本次 case；尝试代码 Agent 与观测工具协同但不预设一定更好 |

## 产品事实与待验证事项

- 官方把 [Obsy Agent Teams](https://docs.guance.com/agent-teams/) 描述为可配置 Agent 职责、Skill、MCP 和自动化任务的工作台。其 [Agent 创建文档](https://docs.guance.com/agent-teams/runtime/)说明当前 Agent 采用自托管运行方式，因此不假设完全免部署、免维护。
- [设置中心](https://docs.guance.com/agent-teams/settings-center/)介绍 obs-cli、obs-mcp；接入工具并不自动赋予所有 Agent 可用权限。能否查询目标空间、模型、日志及 API，以工作空间权益和实际配置为准。
- [Obsy AI 服务协议](https://docs.guance.com/agreements/obsy-agent-agreement/)说明任务执行可能产生积分，具体可用区域、套餐与权限以实际服务为准；不得把观测云免费版等同于免费 Agent Teams。
- 官方 [A2A 文档](https://docs.guance.com/en/agent-teams/a2a/)称其协作功能为 Beta、限定授权调用；此次即便仅用一个 Agent，也不能写成多 Agent 协作已验证。

## 公众号 / XHS 交付设计

公众号严格 ≤1500 字、3–5 个正文段落，包含架构视角决策表：独立开发者的问题 → 公平测试边界 → 一组已验证发现 → 选择与局限。XHS 严格 600–800 字，P1–Pn 分页，呈现同一 case、对照表、真实结果和成本边界；没有结果时先保持大纲，不虚构截图。

**最小证据包**：case 说明、只读权限和工具清单、同一时间窗与数据快照、脱敏提示词及回答、人工验证记录、计时与实际费用、观察盲区、运行结果及可公开素材。生产相关信息经脱敏和授权后才可发布。
